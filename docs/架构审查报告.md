---

## 1. 系统架构概览

### 1.1 项目定位

这是一个基于 React + TypeScript 的**小说创作辅助工具**，旨在帮助作者进行小说的世界观设定、角色塑造、情节设计、章节规划和正文撰写。

### 1.2 技术栈

- **前端**: React 18 + TypeScript
- **状态管理**: Zustand (切片化状态管理)
- **后端**: Express.js + TypeScript
- **数据库**: MySQL (Prisma ORM) + IndexedDB (浏览器本地存储)
- **图谱数据库**: Neo4j (知识图谱存储)
- **AI集成**: Google Gemini API + 智谱 GLM API
- **富文本编辑器**: TipTap
- **可视化**: D3.js + React Flow

### 1.3 核心功能模块

- 世界观构建 (WorldBuilder)
- 角色创作 (CharacterCreator)
- 情节编织 (PlotWeaver)
- 章节规划 (ChapterOutliner)
- 正文撰写 (DraftingRoom / Forge)
- 知识图谱 (KnowledgeGraph)
- Echo系统 (状态变更追踪)
- 创作罗盘 (CreativeCompass)

### 1.3 数据流向分析

```
+-------------------+     +-------------------+     +-------------------+
|   用户操作      | --> |   Zustand Store    | --> |   API Service     |
+-------------------+     +-------------------+     +-------------------+
                                                |
                                                v
+-------------------+     +-------------------+
|   后端API        | <-- |   Prisma ORM       |
+-------------------+     +-------------------+
                                                |
                                                v
+-------------------+     +-------------------+
|   MySQL          |     |   Neo4j           |
+-------------------+     +-------------------+

核心数据流:
1. 用户编辑 -> updateProject() -> Zustand状态更新
2. 状态变化 -> syncToBackend() -> PUT /api/projects/:id/full (全量同步)
3. 状态变化 -> syncToBackend() -> PATCH /api/projects/:id (增量同步)
4. 后端同步 -> syncProjectToGraph() -> Neo4j图谱更新 (异步)
5. AI生成 -> geminiService -> Gemini/GLM API -> 返回数据 -> safeParseAiJson验证 -> 更新状态
```

### 1.5 API端点结构

#### 项目API (`/api/projects`)

- `GET /` - 获取项目列表
- `GET /:id` - 获取单个项目
- `POST /` - 创建项目
- `PUT /:id/full` - 全量同步项目
- `PATCH /:id` - 增量更新项目
- `DELETE /:id` - 删除项目
- `GET /:id/chapters/:chapterId` - 获取章节内容
- `POST /:id/echoes/batch-accept` - 批量接受Echo
- `POST /:id/echoes/batch-reject` - 批量拒绝Echo

- `POST /:id/echoes/undo-batch` - 撤销批量操作

- `GET /:id/echoes/batch-history` - 获取批量操作历史

#### 图谱API (`/api/graph`)

- `GET /:projectId` - 获取项目图谱
- `GET /:projectId/neighbors/:nodeId` - 获取节点邻居
- `GET /:projectId/path` - 获取节点路径
- `GET /:projectId/subgraph` - 获取相关子图
- `GET /:projectId/insights` - 获取叙事洞察
- `GET /:projectId/foreshadowing` - 获取未回收伏笔
- `POST /:projectId/edge` - 创建边关系
- `POST /:projectId/sync` - 手动同步图谱
- `POST /:projectId/merge` - 合并分支
- `GET /:projectId/factions` - 获取派系分组
- `POST /:projectId/propagate` - 模拟蝴蝶效应
- `GET /:projectId/conflicts/*` - 获取冲突信息
- `GET /:projectId/characters/:id/*` - 获取角色图谱信息
- `GET /:projectId/echoes/*` - 获取Echo图谱信息
- `GET /:projectId/chapters/:id/*` - 获取章节图谱信息
- `GET /:projectId/forge-context` - 获取Forge上下文
- `POST /:projectId/forge-sync` - 同步Forge结果

## 3. 潜在问题和改进建议
### 3.1 架构层面问题
| 问题 | 严重程度 | 描述 | 改进建议 |
|-----|----------|------|------|
| 全量同步效率低 | 高 | `PUT /api/projects/:id/full` 使用delete-all + createMany模式， 实现"脏写"机制，增量更新数据 |
| 图谱同步耦合度高 | 中 | Neo4j同步是异步fire-and-forget，失败不感知 | 添加同步状态反馈机制，或 失败时自动重试 |
| 缺少API版本控制 | 中 | 所有API没有版本号 | 添加API版本前 (如 /api/v1/projects) |
| 缺少请求验证 | 中 | 路由层缺少统一的请求验证中间件 | 添加express-validator或zod中间件 |
| 缓存失效策略缺失 | 中 | apiService使用内存缓存，但缺少失效策略 | 添加缓存过期时间和LRU淘汰机制 |
| 章节懒加载覆盖 | 中 | 章节内容按需加载，但同步时会覆盖 | 实现更精细的合并策略，保留已有内容 |
| 图谱查询缺少分页 | 中 | 大项目图谱查询可能返回大量数据 | 添加分页和限制参数 |
| Echo批量操作历史内存存储 | 中 | batchOperationHistory存储在内存中 | 持久化存储或使用Redis |

### 3.2 代码质量问题
| 问题 | 严重程度 | 描述 | 改进建议 |
|-----|----------|------|------|
| 类型定义分散 | 中 | 类型定义在多个文件中重复 | 统一到types.ts或创建types目录 |
| 错误处理不一致 | 中 | 有些地方用try/catch，有些用Promise.catch | 绁一错误处理策略，使用Result类型 |
| BigInt序列化 | 低 | BigInt序列化逻辑在多处重复 | 提取为工具函数 |
| 硬编码API地址 | 低 | API_BASE硬编码为localhost:3001 | 移至配置文件 |
| 缺少单元测试 | 高 | 项目缺少单元测试覆盖 | 添加Jest/Vitest测试框架 |
| 缺少API文档 | 中 | 没有OpenAPI/Swagger文档 | 添加Swagger/OpenAPI文档 |

### 3.3 安全问题
| 问题 | 严重程度 | 描述 | 改进建议 |
|-----|----------|------|------|
| CORS配置宽松 | 中 | 当前允许所有来源 | 配置具体的允许来源白名单 |
| 缺少请求体大小限制 | 低 | 部分API没有请求体大小限制 | 添加请求体大小限制中间件 |
| 缺少认证授权 | 高 | API完全开放，没有认证机制 | 添加JWT/API Key认证 |
| SQL注入风险 | 高 | 虽然使用Prisma ORM，但应审查原始查询 | 审查所有数据库查询，使用参数化查询 |
| 图谱注入风险 | 高 | Neo4j查询应审查 | 审查所有Cypher查询，使用参数化 |
| 敏感信息暴露 | 中 | 错误信息可能暴露内部结构 | 统一错误响应，隐藏详细信息 |
### 3.4 性能问题
| 问题 | 严重程度 | 描述 | 改进建议 |
|-----|----------|------|------|
| 前端包体积大 | 中 | 打包后的JS文件可能较大 | 代码分割、懒加载、Tree-shaking |
| 图谱查询慢 | 中 | 复杂的图谱查询可能较慢 | 添加查询缓存，优化Cypher查询 |
| 状态订阅粒度粗 | 中 | 组件订阅整个project对象 | 使用Zustand选择器，精确订阅 |
| 缺少连接池 | 高 | Neo4j每次查询创建新Driver | 实现Driver连接池 |
| 缺少请求限流 | 中 | 没有API请求限流机制 | 添加请求限流中间件 |
